# 自動登録の精度と Golden データ

Webhook の判定は、条件が揃った候補を人が見ずに公開する（候補は `isVerified: true` で登録される）。誤登録のコストが高いので、「登録できる件数」より「登録したものが合っている割合」を優先する。この文書は、その精度をどう測り、どの規則で守っているかをまとめる。

## Golden とは

D1 に登録済みの、**人手で修正されたイベント**を正解とする。AI の注釈（本文からの暫定ラベル）で作ったコーパスは、主評価には使わない。

- 正解は D1 だけ。ベンチマークの入力は投稿の公開項目だけで、正解は採点でだけ読む。
- 娘（`characterIds`）の正解は D1 に明示があるものだけ。空は「未注釈」で、比べない。
- 元データは `.wrangler/benchmarks/d1-gold/`（無視されるディレクトリ。コミットしない）。
  - `cases.json`: 投稿と D1 の正解イベント。`split.json`: 分割。`run-v15-100/`、`run-v15-test/`: 実 AI の保存応答。

## 開発用と検証用に分ける理由

| 分割 | 投稿 | 正解イベント | 役割 |
| --- | --- | --- | --- |
| dev（開発用） | 100 | 114 | 保留規則を**考えるのに使った**投稿。数字は規則に合わせた結果で、過学習している可能性がある |
| test（検証用） | 174 | 206 | 規則を決めた後に初めて AI に通した投稿。**規則の効果は検証用の数字で見る** |

規則は開発用を見て作り、検証用で当てはまるかを確かめた。両方で効く規則だけを採用している。別枠（投稿日が D1 の開始日より後など）は主指標に混ぜず、このコーパスには含めない。

補助として、規則を作るときに見ていない投稿（extra-start: D1 のイベントの開始参照が指す投稿）30 本・正解 44 件も測った。ただし標本が小さく、登録も 8 件しかないので、**改善と言い切る根拠にはしない**。投稿 ID は dev / test と重ならないが、D1 のイベント単位では 44 件中 17 件が dev / test の正解イベントと共通で、規則が見たイベントを含む（独立な検証ではない）。

## 指標

- **登録**: 判定が `register` になった候補の数（文脈だけから作った候補は本番では登録されないので除く）。
- **登録の precision**: 全項目一致の登録 ÷ 登録。正解に対応づかない登録は不正解に数える。
- **全項目一致の登録率**: 全項目一致の登録 ÷ D1 の正解イベント数。取りこぼしを見る指標で、precision とはトレードオフ。
- 全項目一致 = 店舗・種類・開始日・終了日・購入額・配布数・条件の種類が正解と同じ（娘は D1 に明示があるときだけ。バックフィル後の意味は「限界」の節を参照）。

### 終了日の扱い（R1 を主指標、strict を参考）

D1 の `endDate` は、イベントが終わった後に人が確定した値で、**開始時点の投稿からは取れない**。そのため、候補に終了日が無いことを誤りとは数えない。

- **R1**（`announce-time`。主指標）: 候補に終了日が無ければ、D1 の終了日が何であっても一致。候補に終了日があるときは、D1 と同じ日付のときだけ一致（D1 に終了日が無いのに候補にあるものは不一致）。実測では、候補に終了日があって D1 と食い違う登録は 0 件。
- **strict**（参考）: 候補の終了日 = D1 の終了日（終了日なし同士も一致）。これまでの数字はすべてこの定義で、採点コード（`scripts/lib/event-detect/d1-gold-compare.ts`）の既定も strict のまま。
- 登録の可否と終了日以外の項目の比較は、2 通りで同じ。違うのは終了日の一致だけ。採点の報告（`report.json` / `report.txt`）と回帰テストは、R1 を先に、strict を併記する。

## 現在の数字（v15、実 AI の保存応答を現行の判定で再評価）

店舗・娘は「最上位の確率が **70% 以上なら 2 段目の確認なしで確定**、70% 未満なら確認の『はい』が 70% 以上のときだけ確定」（下の「店舗・ビッカメ娘の採用」）。保留規則は COND・ESN・CHG の 3 つ。件数の監査は「なし」と「あり」を分けて載せる（**本番は 90% の監査あり**）。全項目一致と precision は **R1 / strict** の順。

**実 AI は呼んでいない。** コミットした `scripts/data/d1-gold/fixture.json` の保存応答（v15）を、現行の `evaluateDetection` で再評価した数字。**保存応答には 2 段目（確認）の回答が無いので、70% 未満の店舗・娘は確認で確定できず、採用されない。この数字は「2 段目を受けられない保存応答での下限」で、実運用では 70% 未満の候補が確認の「はい」で拾われるため、登録数はこれより多くなる。** 拾われた分の精度は、実 AI で測っていないので分からない。基準・extra-start の行は、旧版の下限 30% のときの実測で、測り直していない（extra-start の保存応答はフィクスチャに含まれない）。

## 保留規則（`packages/shared/src/event-detect/detection.ts`）

登録に進む候補を保留にする。理由コードは既存の理由と併記される。新規の告知・開始の投稿にだけ付ける。

| 規則 | 理由コード | 保留する条件 | 効果（止めた不正解 / 失った正解。R1） |
| --- | --- | --- | --- |
| COND | `condition_pattern_unconfirmed` | 条件が `[everyone]` のみ、または購入（金額あり）＋先着（配布数あり）の 2 件ちょうど、のどちらでもない | 検証用 12 / 1、開発用 + 検証用 21 / 1 |
| ESN | `extraction_store_unspecified` | 抽出段階の開催店舗候補（`storeKey`）が無い | ESN と CHG を COND の上に足した差（COND のみ → 現行の 3 規則）で、検証用 2 / 1、開発用 + 検証用 4 / 1 |
| CHG | `charge_condition_unconfirmed` | 条件に入金・チャージを含む | D1 に入金条件のイベントが 0 件で評価不能。確認できる正解が無いため保守的に保留（END を含む組での比較では、ESN の上に足しても登録は変わらなかった） |

採用しなかった規則:

- **END（名刺で終了日が無い候補を保留する）**: 試して外した。D1 の終了日は終了後に確定した値で、開始時点の投稿には無いのが普通なので、R1 では、他の規則が全部入った上で END を足しても、止めた不正解 11 / 失った正解 11（開発用 + 検証用）だった。事前に決めた基準（止めた不正解が失った正解の 2 倍以上なら残す）を満たさず、外した。strict では 20 / 2 に見えるが、それは候補に終了日が無いことを誤りと数えたため。
- 画像の有無（止めた不正解 8 / 失った正解 5 で効果が不明確）、1 キャンペーン固定（TRIP）、複数候補（MUL。正解も失う）。

### 店舗・ビッカメ娘の採用（最上位が 70% 以上は確認不要、未満は確認）

規則は 2 つだけ（`detection-association.ts`。判定と確認の対象選択が同じ関数・同じ値を使う）。

- **1 段目の最上位の確率が 70% 以上 → 2 段目の確認は聞かず、確定（採用）する。** ちょうど 70% も確定する。確認の回答が応答にあって低くても、確認は見ない。
- **70% 未満 → 2 段目の「これで合っていますか」（はい/いいえ）を聞き、「はい」の確率が 70% 以上のときだけ確定する。** 未満（回答の欠落を含む）は採用しない（店舗は `store_confirm_low` + `store_unconfirmed` で保留）。

`multiple` と `none` は確率が高くても店舗・娘として採用しない（保留）。確認の対象にもならない。確認の対象になるのは、最上位が具体的な店舗・娘で、かつ確率が 70% 未満のときだけ（確率が取れない・欠けた回答は 70% 未満として扱い、確認を聞く側に倒す）。

しきい値は 4 つ（`store`・`store_confirm`・`character`・`character_confirm`）で、**既定はどれも 70%、管理画面で変更できる（保存した値が優先する）**。意味は、`store`・`character` が「この確率以上なら確認を省いて確定する下限」、`store_confirm`・`character_confirm` が「確認の『はい』がこの確率以上なら確定」。共通値（必須項目の選択閾値）には依らない。

**確認の質問を送っていない保存データ（v15 以前）の 70% 未満は、採用しない。** 旧版は「確率の下限 30% 以上なら採用」で、確認が無ければ関門を掛けなかったが、新しい規則では 70% 未満を確定できるのは確認の「はい」だけなので、確認を聞いていないデータは確定できない。**旧データの再評価は厳しくなる（意図した変更）。** 確認を聞いたのに通らなかったときだけ `store_confirm_low` を付け、聞いていないデータには付けない。

**v16・v17 の保存データ（全員に確認を聞いていたもの）のうち、最上位が 70% 以上のものは、確認を見ずに採用する。** 確認が回答にあって低くても採用する。このとき、回答表の choice 行は確認の行があるので「—」になり、確認の行は「未確定」と出るが、登録は止まらない（下の「回答表」）。

### 回答表（`describeAnswers`）

- choice 行（店舗・対象ビッカメ娘）のしきい値は `thresholdOf` が返す値（既定 70%、保存した値があればその値）。70% 以上なら「確定」、未満なら「未確定」。
- **対応する確認の行（`store_confirm` / `character_confirm`）が回答にある choice 行は、しきい値と判定を「—」にし、未確定の強調（`bg-warning/10`）も付けない。** 判定は直下の確認の行が担う（「確認が確定なら choice が確定かどうかはどうでもいい」）。確率・回答・次点は出す。確認の行が無い choice 行（v15 以前）は、しきい値と確定・未確定を従来どおり出す。保存済みの回答だけから決めるので、request は再生成しない。
- v16・v17 の保存データで、最上位が 70% 以上・確認が低い行は、choice 行が「—」、確認の行が「未確定」なのに登録されている、という見え方になる（上の「確認を見ずに採用する」ため）。回答だけから描く表では、確認を聞いたことと 70% 以上で確認を見なかったことを区別できない。

### 対象ビッカメ娘: 指定がなければ店舗の娘

規則は「**ビッカメ娘の値が明示されていないときは、その店舗のビッカメ娘**」（`packages/shared/src/event-detect/detection-character.ts`）。登録する `characterIds` は、明示されていなければ採用した店舗の ID（店舗キー）にして、保留しない。判定の規則は変わらない。

手動で作ったイベントなどには、娘が空（`event_characters` が 0 件）のものがあり、公開サイトでは「対象未判定」と表示される。`scripts/backfill-event-characters.ts`（`bun run events:backfill-characters`）が、そのイベントに開催店舗の娘を明示で書き込む。バックフィル後は D1 にも店舗の娘が明示で入る（複数店舗なら店舗ごとの娘を全部）。

日次・週次のまとめ（`mergeKey`・`groupRows`）と通常名刺の重複排除（`deduplicateRegularCards`）では、娘の集合が開催店舗の集合とちょうど同じ（店舗キーと同じ ID だけ。バックフィルが入れる既定）なら、娘が空のイベントと同じに見る（`explicitTargetCharacters`）。店舗の娘に別の娘を足した場合や、開催店舗の一部だけを明示した場合は、そのまま明示として扱う。バックフィルで行が分かれたり、名刺が消えたりしないため。表示の公開側（ツイート本文・OG 画像・詳細）は、娘をそのまま表示する。

| 娘の回答 | 登録する娘 |
| --- | --- |
| 最上位の確率が 70% 以上の具体的な娘（店舗と別の娘、店舗と同じ ID の娘とも） | **明示**: その娘（確認は聞かない） |
| 70% 未満で、2 段目の確認の「はい」が 70% 以上の具体的な娘 | **明示**: その娘 |
| 70% 以上の `other`・`secret` | **明示**: その値（D1 にも `other`・`secret` がある） |
| 70% 未満の `other`・`secret` | **明示なし**: 採用した店舗の娘 |
| 最上位が `store_character`（v17。本文でビッカメ娘に言及なし） | 確率に依らず、採用した店舗の娘 |
| 70% 未満で、確認が低い・確認の質問が無い・確認の回答が欠けている（最上位が `none`・`multiple` 以外） | **明示なし**: 採用した店舗の娘（確認が低い = 本文から読めない）。`character_confirm_low` は付けない |
| `multiple`（共同デザイン）、または店舗が具体的で娘だけ `none`（確率に依らない） | 保留（`character_unconfirmed`）。両方 `none`（共通値以上）は従来どおり対象外 |
| 店舗が採用されない（`none`・`multiple`・70% 未満で確認が低い／無い）、または店舗の ID が EventCharacter でない | 店舗の娘にできない。保留（`character_unconfirmed`。娘の確認が低ければ `character_confirm_low` を併記） |

`character_confirm_low` は、店舗が採用されず保留になるときの理由として残す。画面の回答表の娘の確認の行は確率だけで「未確定」と出る。判定では、その娘を明示されていないものとして店舗の娘で登録するので、表と登録された娘が食い違って見えることがある。

### 設定（KV）との関係

- 項目別のしきい値は **12 項目**（回答表の質問の順）: 状態・配布物・開催・配布店舗・開催・配布店舗の確認・対象ビッカメ娘・対象ビッカメ娘の確認・開始日・終了日・配布数・配布条件・購入額・入金・チャージ額（`FIELD_THRESHOLD_KEYS`）。管理画面の「項目別の選択閾値」にこの 12 行が出る。回答表に出る質問のうち、`is_event`（「イベント判定の登録閾値」が別にある）と `single_event`（廃止した項目）は含めない。旧版の `venue.*` / `character.*`（noul）は共通値を使う。回答表の質問と項目別のしきい値の対応が崩れたら落ちるテストがある。
- **既定 70% と保存値の優先**: `store`・`store_confirm`・`character`・`character_confirm` の既定は 70%（共通値には依らない）。**管理画面で保存した値が優先する。** `charge_amount` の既定は共通値（`category`・`start_date` などと同じ）で、未保存なら従来と同じ判定になる。
- **本番に保存された店舗 90% は、そのままでも登録を止めない。** 新しい規則では、保存値が高いと確認を聞く回数が増えるだけ（最上位 90% 未満は確認で決まる）。70% にしたければ、管理画面で「開催・配布店舗」を保存し直す。コードでは KV を書き換えない（ローカルのスナップショットには `store: 0.9` が入っている）。
- **保存値・API の互換**: KV に保存された旧 8 項目の設定は、そのまま読める（`StoredFieldThresholdsSchema`。後から足した `store_confirm`・`character`・`character_confirm`・`charge_amount` は任意で、足りない項目は既定値になる）。旧 9 項目（`single_event` を含む）の保存値から `single_event` だけを取り除く移行も、新しいキー構成で動く。保存 API のリクエストも、新しい 4 項目は任意（古い PWA が 8 キーで保存しても 400 にしない）。状態のレスポンスは常に全 12 項目。余分なキーは不正（`strictObject` の方針は保つ）。
- 「両方 none のときだけ対象外」は、共通値（既定 90%）で判定する（1 段目の 70% ではない）。

## 2 段目の確認（v16）

1 段目（店舗・娘の choice）の最上位が具体的な店舗・娘で、かつ確率が 70% 未満のとき、別の Clef 呼び出しで「この店舗開催ですか」「対象ビッカメ娘はこのキャラクターですか」を、はい/いいえ（noul）で聞く（`association-confirm.ts`）。70% 以上は確認なしで確定するので聞かない（2 段目の呼び出しも減る）。「はい」の確率が下限（`store_confirm`・`character_confirm`、既定 0.7）未満なら、店舗は確定せず `store_confirm_low` で保留にする。娘は、確認が低いと本文から読めない（明示されていない）ので、保留にせず採用した店舗の娘で登録する（上の「対象ビッカメ娘: 指定がなければ店舗の娘」）。

**店舗の娘にも娘の確認を聞く（二回チェック）。** 要件は「配布店舗とビッカメ娘は二回チェックする（1 段目 choice → 2 段目 はい/いいえ）」。「特に指定がなければその店舗の娘」は、娘が**未指定のときの既定値**（`detection-character.ts`）の話で、2 回目のチェックを省く意味ではない。そのため、最上位の娘が最上位の店舗と同じ ID（店舗の娘）でも、具体的な娘で確率が 70% 未満なら娘の確認を聞く（`confirmTargetOf`）。確認の対象にならないのは、確認する具体的な娘が無いとき（`store_character`＝本文に言及なし、`other`・`secret`・`multiple`・`none`）と、確率が 70% 以上のとき。質問文・state の行（`確認対象のビッカメ娘: 新横たん`）・プロンプトの版は変えていない（変わるのは「どの投稿で聞くか」だけ）。

- **店舗の娘は、娘の確認が低くても登録を止めない。** 娘の確認が下限未満でも、保留にせず、採用した店舗の娘で登録する（`character_confirm_low` は付けない）。同じ ID なので、確認が通っても通らなくても登録される娘は同じ。店舗の確認が低いときの保留（`store_confirm_low`）は従来どおり。
- **効果は回答表で確認できること。** 本番（v0.38.1）の受信詳細では、開催・配布店舗＝新横浜店（80.5%）→ 開催・配布店舗の確認＝はい 97.6%、対象ビッカメ娘＝新横たん（78.9%）なのに、娘の確認の行が無かった。店舗の娘にも娘の確認が出る（確率が 70% 未満のとき）。
- 2 段目は 1 リクエストにまとめて送るので、確認を聞く投稿でも呼び出しは 1 回（店舗と娘の 2 問）。
- 確認の質問を送っていない保存データ（v15 以前）の 70% 未満は採用しない（上の「店舗・ビッカメ娘の採用」）。`isConfirmedYes` は質問が無ければ「確認では確定できない」を返す（以前の `passesConfirm` の「質問が無ければ通す」は廃止）。
- **回帰の測定の限界。** フィクスチャの保存応答（v15）には 2 段目の回答が無く、確認の質問を含まない request では 70% 未満を確定できないので、上の「現在の数字」は下限。実 AI で測ったわけではない。

## 運用上の注意

KV の保存値の変更はこの変更に含めない（件数の監査の環境変数だけは、下のとおり 0.7 に揃えた）。登録を増やすかどうかは、次の 2 点を確かめてからの運用判断になる。

- **件数の監査（本番では関門として使わなくなった）**: 件数の監査の結果は、自動登録を止めない。画面にも出さず、抽出段階の不一致のときの再抽出と、`extraction_json` への記録にだけ使う。以下は、関門だった頃の運用の記録で、評価表の「本番」「90%」「件数の監査 70%」の数字は、すべて関門があった前提の数字になる。`scripts/` の評価は、今も関門を掛けた状態を「本番と同じ」として計算するため、現在の本番とは一致しない。

  関門だった頃の記録: 監査が保存応答の大半を止めるので、規則を入れても本番の登録はほぼ 0 件のままだった（検証用では 173 投稿中 165 投稿の件数質問が 90% に届かない）。しきい値は環境変数 `EVENT_DETECTION_ITEM_COUNT_THRESHOLD`（`workers/web/wrangler.toml`）で、3 環境とも `0.9` から `0.7` に変えた。このため上の評価表の「本番」「90%」は変更前の設定の数字で、現在の本番設定は「件数の監査 70%」の行に当たる。コードの既定 `DEFAULT_ITEM_COUNT_THRESHOLD`（0.9）と `scripts/` の評価は、再現性のため 0.9 のまま変えていない。
- **店舗のしきい値は KV の保存値が優先**: 本番の KV に `store: 0.9` が保存されている。新しい規則では、保存値が高いと確認を聞く回数が増えるだけで、登録は止まらない（90% 未満の店舗は確認の「はい」で決まる）。既定の 70% にしたければ、管理画面で「開催・配布店舗」を保存し直す。

## 回帰テスト

`__tests__/d1-gold-regression.test.ts` が CI で精度の下限を守る。実 AI は呼ばず、コミットした `scripts/data/d1-gold/fixture.json` の保存応答を現行の `evaluateDetection` で再評価する。規則の単体は `__tests__/d1-gold-regression-rules.test.ts`。

- フィクスチャは v15 の 1 段目の質問で作られていること（`detectionVersion` が `v5-webhook-v15-concise-author`）、かつ現行（v16 以降）の 1 段目の質問がそれと同一であること（フィクスチャの全候補から作った 1 段目の request の sha256 を固定している）。**1 段目の質問が変わったらハッシュが合わなくなり、再作成が必要**と表示して失敗する。v16 は 2 段目（確認の質問）を足した版で、フィクスチャには確認の回答が無いため、確認の質問を含まない request として再評価する（判定は v15 のときと変わらない）。確認の回答を含むフィクスチャへの再作成は、v16 を実 AI で測り直した後に行う。
- 内容のハッシュ（正規化した JSON）が一致すること。
- 開発用・検証用それぞれで、登録数と precision が下限以上、全項目一致が基準より多く失われていないこと。下限は主指標の R1 に置く（開発用: 登録 17・precision 80%・全項目一致 15 以上、検証用: 登録 57・precision 65%・全項目一致 40 以上。70% 以上のみ採用での実測は 20 / 90.0% / 18 と 62 / 71.0% / 44）。strict の実測（開発用 14、検証用 36）は参考として別のテストで見る。**下限を緩めた理由は、保存応答に 2 段目の回答が無いため、70% 未満を採用できないこと**（精度が下がったからではない）。
- 店舗のしきい値は、既定 70% を明示して評価する（`withStore(STORE_DEFAULT_THRESHOLD)`）。本番の KV のスナップショット（保存値 0.9）のままだと、保存応答に 90% 以上の最上位が無いため登録が 0 件になることも、別のテストで見る。店舗のしきい値を下げるほど登録が増える（単調）ことも見る。
- 娘の既定（指定がなければ店舗の娘）について、`character_unconfirmed` の保留が、店舗が採用されないものか、娘の最上位が `multiple`・`none` のものだけであること、登録した候補の娘が 1 件で空でないことも、別のテストで見る。

### フィクスチャの作り方

```sh
bun scripts/export-d1-gold-fixture.ts
```

`.wrangler/benchmarks/d1-gold/` の保存応答（読むだけ）から、約 1.1 MB の `fixture.json` を作る。確率の分布は上位 8 件に切り詰め、小数 3 桁に切り捨てる（判定のしきい値は全て 0.001 の倍数なので、「しきい値以上」の結果は変わらない）。切り詰めたフィクスチャと元の保存応答で、全候補の判定（状態・理由・候補）が一致しなければ、書かずに止まる。質問（選択肢の説明）は持たず、現行のソースから作り直す。

`DETECTION_VERSION` を上げたとき（質問を変えたとき）は、新しい版で測定し直した保存応答が必要になる。測り直す手順は次の節。

## 実 AI で測り直す手順

実 AI（評価 API）を使うので、**使う前に必ず確認を取る**。開発サーバー（`bun dev`、15175）が動いていること。ローカルの評価 API だけを使い、D1・通知・本番への書き込みはしない。

```sh
# 分割の確認（AI は呼ばない）
bun scripts/benchmark-d1-gold.ts --split test
# 実 AI（検証用）。上限は 900 回、同時 2 本、自動再試行なし
bun scripts/benchmark-d1-gold.ts --split test --live --directory .wrangler/benchmarks/d1-gold/run-v15-test
# 採点（AI は呼ばず、保存応答を現行のソースで再評価する）
bun scripts/benchmark-d1-gold.ts --split dev,test --score .wrangler/benchmarks/d1-gold/run-v15-test --out .wrangler/benchmarks/d1-gold/score-v15-baseline
```

- 開発用は測定済みなので再送しない（`--live` は拒否される）。
- 呼び出しの台帳（`live-attempts.jsonl`）は送信の前に追記する。上限（検証用は 900 回）を超えると止まる。
- 502 などの通信エラーが出ると、**測定全体が止まる**（その場では自動で再試行しない）。同じコマンドを再実行すると、完了していない投稿だけを再送する。同じ投稿の通信失敗は再実行をまたいで通算 3 回までで、3 回目の失敗でその投稿をエラーとして記録し、以後は再送せず次の投稿へ進む。応答の検証に失敗した投稿は再送しない。完了した投稿は再送しない。
- 負荷が高いと評価 API が 502 を返す。ほかの重い処理（全体のテスト・ビルド）と同時に実行しない。

## 限界
