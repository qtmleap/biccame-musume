# 自動登録の精度と Golden データ

Webhook の判定は、条件が揃った候補を人が見ずに公開する（候補は `isVerified: true` で登録される）。誤登録のコストが高いので、「登録できる件数」より「登録したものが合っている割合」を優先する。この文書は、その精度をどう測り、どの規則で守っているかをまとめる。

## Golden とは

D1 に登録済みの、**人手で修正されたイベント**を正解とする。AI の注釈（本文からの暫定ラベル）で作ったコーパスは、主評価には使わない。

- 正解は D1 だけ。ベンチマークの入力は投稿の公開項目だけで、正解は採点でだけ読む。
- 娘（`characterIds`）の正解は D1 に明示があるものだけ。空は「未注釈」で、比べない。
- 元データは `.wrangler/benchmarks/d1-gold/`（無視されるディレクトリ。コミットしない）。
  - `cases.json`: 投稿と D1 の正解イベント。`split.json`: 分割。`run-v15-100/`、`run-v15-test/`: 実 AI の保存応答。

## 開発用と検証用に分ける理由

| 分割 | 投稿 | 正解イベント | 役割 |
| --- | --- | --- | --- |
| dev（開発用） | 100 | 114 | 保留規則を**考えるのに使った**投稿。数字は規則に合わせた結果で、過学習している可能性がある |
| test（検証用） | 174 | 206 | 規則を決めた後に初めて AI に通した投稿。**規則の効果は検証用の数字で見る** |

規則は開発用を見て作り、検証用で当てはまるかを確かめた。両方で効く規則だけを採用している。別枠（投稿日が D1 の開始日より後など）は主指標に混ぜず、このコーパスには含めない。

補助として、規則を作るときに見ていない投稿（extra-start: D1 のイベントの開始参照が指す投稿）30 本・正解 44 件も測った。ただし標本が小さく、登録も 8 件しかないので、**改善と言い切る根拠にはしない**。投稿 ID は dev / test と重ならないが、D1 のイベント単位では 44 件中 17 件が dev / test の正解イベントと共通で、規則が見たイベントを含む（独立な検証ではない）。

## 指標

- **登録**: 判定が `register` になった候補の数（文脈だけから作った候補は本番では登録されないので除く）。
- **登録の precision**: 全項目一致の登録 ÷ 登録。正解に対応づかない登録は不正解に数える。
- **全項目一致の登録率**: 全項目一致の登録 ÷ D1 の正解イベント数。取りこぼしを見る指標で、precision とはトレードオフ。
- 全項目一致 = 店舗・種類・開始日・終了日・購入額・配布数・条件の種類が正解と同じ（娘は D1 に明示があるときだけ）。

### 終了日の扱い（R1 を主指標、strict を参考）

D1 の `endDate` は、イベントが終わった後に人が確定した値で、**開始時点の投稿からは取れない**。そのため、候補に終了日が無いことを誤りとは数えない。

- **R1**（`announce-time`。主指標）: 候補に終了日が無ければ、D1 の終了日が何であっても一致。候補に終了日があるときは、D1 と同じ日付のときだけ一致（D1 に終了日が無いのに候補にあるものは不一致）。実測では、候補に終了日があって D1 と食い違う登録は 0 件。
- **strict**（参考）: 候補の終了日 = D1 の終了日（終了日なし同士も一致）。これまでの数字はすべてこの定義で、採点コード（`scripts/lib/event-detect/d1-gold-compare.ts`）の既定も strict のまま。
- 登録の可否と終了日以外の項目の比較は、2 通りで同じ。違うのは終了日の一致だけ。採点の報告（`report.json` / `report.txt`）と回帰テストは、R1 を先に、strict を併記する。

本番の設定（店舗・娘 90%）では、確率が選択肢（46 店舗・55 娘）に散るため最上位が 90% に届かず、開発用・検証用のどちらでも登録が 0 件になる。確率のしきい値は、正解と誤りを分けない（項目別のしきい値、店舗・娘の下限、件数の監査は precision を上げなかった）。効くのは次の保留規則だった。

## 保留規則（`packages/shared/src/event-detect/detection.ts`）

登録に進む候補を保留にする。理由コードは既存の理由と併記される。新規の告知・開始の投稿にだけ付ける。

| 規則 | 理由コード | 保留する条件 | 効果（止めた不正解 / 失った正解。R1） |
| --- | --- | --- | --- |
| COND | `condition_pattern_unconfirmed` | 条件が `[everyone]` のみ、または購入（金額あり）＋先着（配布数あり）の 2 件ちょうど、のどちらでもない | 検証用 12 / 1、開発用 + 検証用 21 / 1 |
| ESN | `extraction_store_unspecified` | 抽出段階の開催店舗候補（`storeKey`）が無い | ESN と CHG を COND の上に足した差（COND のみ → 現行の 3 規則）で、検証用 2 / 1、開発用 + 検証用 4 / 1 |
| CHG | `charge_condition_unconfirmed` | 条件に入金・チャージを含む | D1 に入金条件のイベントが 0 件で評価不能。確認できる正解が無いため保守的に保留（END を含む組での比較では、ESN の上に足しても登録は変わらなかった） |

採用しなかった規則:

- **END（名刺で終了日が無い候補を保留する）**: 試して外した。D1 の終了日は終了後に確定した値で、開始時点の投稿には無いのが普通なので、R1 では、他の規則が全部入った上で END を足しても、止めた不正解 11 / 失った正解 11（開発用 + 検証用）だった。事前に決めた基準（止めた不正解が失った正解の 2 倍以上なら残す）を満たさず、外した。strict では 20 / 2 に見えるが、それは候補に終了日が無いことを誤りと数えたため。
- 画像の有無（止めた不正解 8 / 失った正解 5 で効果が不明確）、1 キャンペーン固定（TRIP）、複数候補（MUL。正解も失う）。

店舗は最上位を採用する。`multiple` と `none` は採用せず保留。確率の下限は 0.3（0.3 まで下げても精度は変わらず、ゴミの選択を避けるための値）。

### 対象ビッカメ娘: 指定がなければ店舗の娘

規則は「**ビッカメ娘の値が明示されていないときは、その店舗のビッカメ娘**」。D1 でも娘が明示されるのは店舗の娘と違うときだけで、店舗から推定した娘は書かれていない（`packages/shared/src/event-detect/detection-character.ts`）。登録する `characterIds` は、明示されていなければ採用した店舗の ID（店舗キー）にして、保留しない。

| 娘の回答 | 登録する娘 |
| --- | --- |
| 確率が下限（0.3）以上で、店舗と別の具体的な娘。2 段目の確認が下限以上（確認の質問が無い v15 以前の保存データは関門なしで通る） | **明示**: その娘 |
| 確率が下限以上の `other`・`secret` | **明示**: その値（D1 にも `other`・`secret` がある） |
| 確率が下限以上で、店舗と同じ ID | 店舗の娘（従来どおり） |
| 確率が下限に届かない（最上位が `none`・`multiple` 以外） | **明示なし**: 採用した店舗の娘 |
| 店舗と別の具体的な娘だが、2 段目の確認が下限未満 | **明示なし**: 採用した店舗の娘（確認が低い = 本文から読めない）。`character_confirm_low` は付けない |
| 確率が下限以上の `multiple`（共同デザイン）、または店舗が具体的で娘だけ `none` | 保留（`character_unconfirmed`）。両方 `none` は従来どおり対象外 |
| 最上位が `none`・`multiple` で確率が下限に届かない | 保留（`character_unconfirmed`） |
| 店舗が採用されない（`none`・`multiple`・確率不足・店舗の確認が低い）、または店舗の ID が EventCharacter でない | 店舗の娘にできない。従来どおり保留（`character_unconfirmed`。娘の確認が低ければ `character_confirm_low` を併記） |

`character_confirm_low` は、店舗が採用されず保留になるときの理由として残す（v16 の保存データの理由表示も変わらない）。画面の回答表は変えておらず、娘の行は確率が下限未満のとき「未確定」と出る。判定では、その娘を明示されていないものとして店舗の娘で登録するので、表と登録された娘が食い違って見えることがある。

保存応答（v15）では、娘の最上位の確率が 0.3 未満の候補は 9 件（開発用 2・検証用 7）しか無い。うち 1 件は対象外（キーワードなし）、2 件は店舗が採用されず、2 件は最上位が `multiple` で、どれも変更前と同じ。娘の既定が効いて `character_unconfirmed` が外れるのは 4 件だけで、どれも店舗の食い違い・状態・購入額などの別の理由で保留のまま。登録数は増減しない（下の「現在の数字」は変わらない）。D1 に娘の明示がある 10 候補（dev 6・extra-start 4）では、最上位が正解と一致したのは 4 件で、変更前後とも同じ。

### 設定（KV）との関係

- 項目別のしきい値のキーは増やしていない（`FieldThresholdsSchema` は 8 キーのまま）。KV に保存された設定はそのまま読める。
- `store` の既定値は `min(共通値, 0.3)`。**管理画面で保存した値は、この既定値より優先する。** 本番の KV に `store: 0.9` が保存されていると、新しい既定値は効かず、登録は 0 件のまま。管理画面の「開催・配布店舗」の閾値を 30% に保存し直す必要がある（コードでは KV を書き換えない。ローカルのスナップショットには `store: 0.9` が入っている）。
- 対象ビッカメ娘は専用のキーを持たず、`min(共通値（必須項目の選択閾値）, 0.3)` を下限にする。この下限に届かない娘は「明示されていない」ものとして、採用した店舗の娘になる。
- 店舗・娘とも「両方 none のときだけ対象外」は、共通値（既定 90%）で判定する。

## 2 段目の確認（v16）

1 段目（店舗・娘の choice）で最上位に選んだ具体的な店舗・娘について、別の Clef 呼び出しで「この店舗開催ですか」「対象ビッカメ娘はこのキャラクターですか」を、はい/いいえ（noul）で聞く（`association-confirm.ts`）。「はい」の確率が下限（`STORE_CONFIRM_THRESHOLD`・`CHARACTER_CONFIRM_THRESHOLD`、既定 0.7、`detection-thresholds.ts`）未満なら、店舗は確定せず `store_confirm_low` で保留にする。娘は、確認が低いと本文から読めない（明示されていない）ので、保留にせず採用した店舗の娘で登録する（上の「対象ビッカメ娘: 指定がなければ店舗の娘」）。request に確認の質問が無い保存データ（v15 以前）の判定は変わらない。

**指定がなければ店舗の娘とみなし、娘の確認は店舗と別の娘のときだけ聞く。** 最上位の娘の ID が最上位の店舗の ID と同じ（店舗の娘。`isStoreCharacter`）なら、娘の質問も state の娘の行も作らず、関門も掛けない。D1 で娘が明示されるのは店舗の娘と違うときだけで、店舗から推定した娘は D1 に書かれていない（店舗から推定して確定しない移行方針）ため。店舗が none・multiple で娘が具体的なときは店舗の娘とは言えないので、従来どおり娘を確認する。other・secret は確認しない。店舗の確認は従来どおり。2 段目を送る回数は変わらず、店舗の娘では 1 回あたりの質問が店舗だけになる。v16 の質問文は変えていない。

登録に進む 104 候補（開発用 26・検証用 70・未使用の 30 投稿 8）に、本番と同じ質問を実 AI で聞いた（198 回。測定時は店舗の娘にも娘を聞いた）。保存した回答を、店舗の娘は娘の回答を使わず、確認が低い娘は店舗の娘で登録する現行の挙動で採点し直した結果（開発用 + 検証用の合計、終了日は R1、店舗・娘は最上位採用、件数の監査なし）:

| 確認の下限 | 登録 | 全項目一致 | 精度 | 止めた不正解 | 失った正解 |
| --- | --- | --- | --- | --- | --- |
| 0（関門なし） | 96 | 73 | 76.0% | - | - |
| 0.5 | 96 | 73 | 76.0% | 0 | 0 |
| 0.6 | 92 | 71 | 77.2% | 2 | 2 |
| 0.7（既定） | 88 | 69 | 78.4% | 4 | 4 |
| 0.8 | 77 | 61 | 79.2% | 7 | 12 |
| 0.9 | 57 | 48 | 84.2% | 14 | 25 |

娘の既定を入れる前（確認が低い娘を保留にしていた）の数字は、下限 0.7 で登録 86・全項目一致 67・精度 77.9%・止めた不正解 4・失った正解 6（0.5: 95 / 72、0.6: 90 / 69、0.8: 76 / 60、0.9: 56 / 47）。娘にも聞いていたさらに前の数字（下限 0.7）は、登録 52・全項目一致 41・精度 78.8%・止めた不正解 12・失った正解 32。精度の区間（Wilson 95%）は大きく重なる。

- **娘の確認はもう登録を止めない。** 店舗と別の娘で確認が低いときは、保留ではなく店舗の娘で登録するので、確認の関門が登録を減らすのは店舗の確認だけになり、表は「店舗のみ」の数字と一致する。今回も娘を聞く候補は 2 件（どちらも検証用で全項目一致の登録、「はい」は 0.55 と 0.39）で、下限 0.7 ではどちらも店舗の娘で登録され、他の項目も D1 と一致した（D1 に娘の明示は無く、娘は比べない）。新たに登録に進むのは下限 0.6〜0.7 でこの 2 件（0.5・0.8・0.9 は 0.39 の 1 件）。娘の誤りは 0 件。
- 変更前の数字では、娘の確認が正解を止めていた。104 候補のうち 100 件は店舗の娘で、以前に失った正解 32 件のうち 30 件は娘の確認が関わり、そのうち 28 件が店舗の娘（残り 2 件は店舗と別の娘）。質問が「本文に名前のない娘を推測しないでください」と聞くため、本文に名前が無い店舗の娘は「はい」が低い（名前あり 77 件は中央値 0.92・0.7 以上 77%、語幹のみ・名前なし 25 件は中央値 0.39・0.7 以上 4%）。これは誤りではなく質問の趣旨どおり。店舗の娘は娘の確認を外し、さらに今回、確認が低い娘も店舗の娘で登録するようにした。
- 事前に決めた基準（下限 0.7 で全項目一致の損失が関門なしの 20% 以内）を満たす。73 件が 69 件になり、損失は 4 件（5.5%）。娘にも聞いていた以前は損失 43.8%、店舗の娘の確認を外した後は損失 8.2%（73 → 67）。関門は既定の 0.7 のままにする根拠になる。
- 店舗の確認だけで見た数字と同じ（下限 0.7: 登録 88・全項目一致 69・精度 78.4%・止めた不正解 4・失った正解 4）。
- 店舗は見分けている（正しい店舗の「はい」の中央値 0.93、作為的に聞いた誤った店舗 0.04）。娘も、作為的に聞いた誤った娘には低く答える（中央値 0.11、0.7 以上は 6%）。ただし D1 に店舗の娘の注釈が無く、実際の誤った娘を止められるかは測れていない。
- 本文に娘の名前があるのに「はい」が 0.5 未満の 6 件は、名前が「みっけたん情報」「新横たんよりお知らせ」のような見出し、「本店たんギャラリー」のような場所名、複数の娘の列挙の一つ、別の品物の引用の中にだけ出ていた（質問が「対象物に描かれる娘」を聞くためと推測。確かめてはいない）。
- 費用: 1 投稿あたり追加の Clef 呼び出しは約 1.24 回（関門に届く候補は約 28%）で、呼び出し数は変わらない。
- 測定は店舗と娘をまとめた 1 回の呼び出しで聞いた。店舗の娘では店舗だけを聞くようになるので、店舗の「はい」はわずかに違いうる（測り直していない）。
- **娘の既定で新しく登録に進む候補の関門は、測っていない。** 娘の確率が下限（0.3）に届かず、店舗の娘として登録に進むようになる候補は、保存応答では 0 件（上記）で、店舗の確認の回答も無い。そのため、関門を掛けた数字は出せない。実 AI で測り直したときに、こうした候補の店舗の確認を聞く。

## 運用上の注意

設定の変更はこの変更に含めない。登録を増やすかどうかは、次の 2 点を確かめてからの運用判断になる。

- **件数の監査（本番の 0.9）**: 監査が保存応答の大半を止めるので、規則を入れても本番の登録はほぼ 0 件のまま（検証用では 173 投稿中 165 投稿の件数質問が 90% に届かない）。しきい値は環境変数 `EVENT_DETECTION_ITEM_COUNT_THRESHOLD`（`workers/web/wrangler.toml`。3 環境とも `0.9`）で、コードでは変えていない。70% なら上の表のとおり登録が戻る。
- **店舗のしきい値は KV の保存値が優先**: `store` の既定値は `min(共通値, 0.3)` だが、管理画面で保存した値はそれより優先される。本番の KV に `store: 0.9` が保存されていれば、新しい既定値は効かず、店舗が確定しないまま保留される。

## 回帰テスト

`__tests__/d1-gold-regression.test.ts` が CI で精度の下限を守る。実 AI は呼ばず、コミットした `scripts/data/d1-gold/fixture.json` の保存応答を現行の `evaluateDetection` で再評価する。規則の単体は `__tests__/d1-gold-regression-rules.test.ts`。

- フィクスチャは v15 の 1 段目の質問で作られていること（`detectionVersion` が `v5-webhook-v15-concise-author`）、かつ現行（v16 以降）の 1 段目の質問がそれと同一であること（フィクスチャの全候補から作った 1 段目の request の sha256 を固定している）。**1 段目の質問が変わったらハッシュが合わなくなり、再作成が必要**と表示して失敗する。v16 は 2 段目（確認の質問）を足した版で、フィクスチャには確認の回答が無いため、確認の質問を含まない request として再評価する（判定は v15 のときと変わらない）。確認の回答を含むフィクスチャへの再作成は、v16 を実 AI で測り直した後に行う。
- 内容のハッシュ（正規化した JSON）が一致すること。
- 開発用・検証用それぞれで、登録数と precision が下限以上、全項目一致が基準より多く失われていないこと。下限は主指標の R1 に置く（開発用: 登録 22・precision 80%・全項目一致 20 以上、検証用: 登録 62・precision 65%・全項目一致 46 以上。実測は 26 / 88.5% / 23 と 70 / 71.4% / 50）。strict の実測（開発用 19、検証用 42）は参考として別のテストで見る。
- 娘の既定（指定がなければ店舗の娘）を入れた後に測り直した実測も同じ値で、下限は置き直していない。保存応答には、娘の確率が 0.3 未満の候補が 4 件しか無く、どれも別の理由で保留のままのため。`character_unconfirmed` の保留が、店舗が採用されないものか、娘の最上位が `multiple`・`none` のものだけであること、登録した候補の娘が 1 件で空でないことも、別のテストで見る。

### フィクスチャの作り方

```sh
bun scripts/export-d1-gold-fixture.ts
```

`.wrangler/benchmarks/d1-gold/` の保存応答（読むだけ）から、約 1.1 MB の `fixture.json` を作る。確率の分布は上位 8 件に切り詰め、小数 3 桁に切り捨てる（判定のしきい値は全て 0.001 の倍数なので、「しきい値以上」の結果は変わらない）。切り詰めたフィクスチャと元の保存応答で、全候補の判定（状態・理由・候補）が一致しなければ、書かずに止まる。質問（選択肢の説明）は持たず、現行のソースから作り直す。

`DETECTION_VERSION` を上げたとき（質問を変えたとき）は、新しい版で測定し直した保存応答が必要になる。測り直す手順は次の節。

## 実 AI で測り直す手順

実 AI（評価 API）を使うので、**使う前に必ず確認を取る**。開発サーバー（`bun dev`、15175）が動いていること。ローカルの評価 API だけを使い、D1・通知・本番への書き込みはしない。

```sh
# 分割の確認（AI は呼ばない）
bun scripts/benchmark-d1-gold.ts --split test
# 実 AI（検証用）。上限は 900 回、同時 2 本、自動再試行なし
bun scripts/benchmark-d1-gold.ts --split test --live --directory .wrangler/benchmarks/d1-gold/run-v15-test
# 採点（AI は呼ばず、保存応答を現行のソースで再評価する）
bun scripts/benchmark-d1-gold.ts --split dev,test --score .wrangler/benchmarks/d1-gold/run-v15-test --out .wrangler/benchmarks/d1-gold/score-v15-baseline
```

- 開発用は測定済みなので再送しない（`--live` は拒否される）。
- 呼び出しの台帳（`live-attempts.jsonl`）は送信の前に追記する。上限（検証用は 900 回）を超えると止まる。
- 502 などの通信エラーが出ると、**測定全体が止まる**（その場では自動で再試行しない）。同じコマンドを再実行すると、完了していない投稿だけを再送する。同じ投稿の通信失敗は再実行をまたいで通算 3 回までで、3 回目の失敗でその投稿をエラーとして記録し、以後は再送せず次の投稿へ進む。応答の検証に失敗した投稿は再送しない。完了した投稿は再送しない。
- 負荷が高いと評価 API が 502 を返す。ほかの重い処理（全体のテスト・ビルド）と同時に実行しない。

## 限界

- 本文だけを入力にしている。画像は見えない（`画像: N 枚` の件数だけ渡る）。画像にだけ書かれた情報は正解にならない。
- 娘の正解は D1 に明示があるものだけ。未注釈の娘は評価できず、取り違えは見えない。指定がなければ店舗の娘にする規則は、D1 に娘の明示が無い候補では娘を比べないので、規則が合っているかは D1 では確かめられない（明示がある候補は 10 件のみ）。
- 陰性（イベントではない投稿）は測っていない。誤って登録する投稿の割合（偽陽性）は、陽性だけのコーパスでは過小評価される。
- 検証用の標本は 174 投稿。precision の差が数ポイントのときは誤差の範囲で、規則を足すときは両方の分割で確かめる。
- D1 の正解自体が人手で、ゆらぎがある。終了日は終了後に確定した値なので、開始時点の投稿とは食い違いうる（R1 はその分を誤りに数えない。strict は数える）。
