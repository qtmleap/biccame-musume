# CLAUDE.md

Fan site for the "Biccame Musume" characters. Bun workspaces: `workers/web` (UI + API Worker), `workers/bot` (X posting / timeline Worker), `packages/shared`. See `README.md` for setup and commands.

## Branching

- Never commit directly to `develop` or `master`. If you are about to change code while on either, first run `git switch -c <type>/<short-name>` from `develop`.
- `<type>` is a commitlint type from `.commitlintrc.yaml`: `build`, `ui`, `ci`, `docs`, `feat`, `fix`, `perf`, `refactor`, `revert`, `format`, `test`, `chore`.
- Push the branch and open the PR against `develop`. `master` only receives the release PR from `develop`.
- GitHub protection is minimal: `master` blocks force-pushes and deletions only (no required reviews or checks), and `develop` is unprotected. These rules are enforced by convention, so follow them anyway.

## Commits and merging

- Write commit messages in English Conventional Commits. The header must be 128 characters or fewer (`.commitlintrc.yaml`). CI only lints the last commit of each push (`bun commitlint --last`).
- Always merge with a merge commit (no squash, no rebase), for feature -> `develop` and `develop` -> `master`. `backmerge.yaml` fast-forwards `develop` to `master` after a release, and it only warns, without syncing, when `develop` cannot be fast-forwarded.
- Merge commit subject: `<type>(<scope>): merge PR #<n> <summary>`, for example `fix(events): merge PR #117 keeping event list url as opened`. A release uses `chore(release): merge PR #<n> releasing v<version>`.

## Releases

Follow `.claude/release.json`.

- The version source is only the root `package.json` (the app build reads it too). Do not use the `version` in `workers/web/package.json`.
- Bump it in a separate PR titled `chore: bump version to X.Y.Z` and merge that into `develop` first.
- Open the release PR `develop` -> `master` titled `release: v{version} ...` and merge it with a merge commit.
- Tag the merge commit with an annotated tag `v{version}` (message `release v{version}`). Do not create a GitHub Release.

## Deployment side effects

- Merging a PR into `develop` deploys staging (`dev.biccame-musume.com`). Merging into `master` deploys production (`biccame-musume.com`). `.github/workflows/deployment.yaml` runs D1 migrations, badge seed, app, then bot, in that order.
- Never run production deploys, remote D1 writes (`--remote`, `badges:seed remote-*`), or bot activation (`--allow-active-production`) by hand without explicit approval.

## Verify before pushing

CI runs on `push` only. Run the same checks locally:

```sh
bun run generate        # Prisma Client is gitignored; required before typecheck and test
bun run typecheck
bun run test            # plain `bun test` skips packages/shared
bun biome check workers/web/src workers/bot/src packages/shared/src __tests__
```

The `biome-plugins` git submodule must be initialized (`git submodule update --init`) or Biome cannot load its rules.

When `prisma/schema.prisma` changes:

- Create a migration with `bun run migrate:new --name <name>`, then apply it locally with `bun run migrate`.
- Check it the way CI does: `bunx prisma migrate diff --from-migrations ./prisma/migrations --to-schema ./prisma/schema.prisma --config ./prisma/prisma.config.ts --exit-code`.

## D1 migration pitfall

If a generated migration contains `PRAGMA foreign_keys=OFF` with a table rebuild (`RedefineTables`), do not apply it as is. D1 ignores that pragma, so `DROP TABLE` cascades into child tables and deletes their rows. Rewrite it to copy the child tables into backup tables first and restore them after the rebuild. The working example is `prisma/migrations/20260807175125_fix_events_group_fk/migration.sql`.

## Generated or vendored files: do not edit by hand

- `workers/web/src/api/db/generated/prisma/`: run `bun run generate`.
- `workers/web/src/app/routeTree.gen.ts`: generated by TanStack Router.
- `packages/shared/src/generated/bot-stores.json` and `closed-store-keys.json`: regenerate with `bun scripts/generate-bot-stores.ts`; `bun run check:bot-stores` verifies it.
- `workers/web/src/app/components/ui/**`: shadcn components. Change styles through `className` at the call site.

## Code conventions

Enforced by Biome (`biome.json`) and the `biome-plugins` submodule. The plugin rules are warnings, so CI does not fail on them, but never add new violations.

- No `let`; use `const`.
- No `new Date()`; use `dayjs`.
- No `??` and no `||` fallbacks to `''`, `[]`, `{}`, `null` or `undefined`; fix the schema or type instead.
- No `as` type assertions (`as const` is fine) and no `any`.
- No `while` or `do...while`.
- Zod: use `safeParse` instead of `parse`, `.nonempty()` instead of `.min(1)`, `z.url()` / `z.uuid()` instead of `z.string().url()` / `.uuid()`; do not use a bare `z.string()` or `.optional()` / `.nullable()` on arrays and booleans.
- Define functions with `const`, not `function`. Use `async/await`.
- Write comments in Japanese and log messages in English.
- Use `lucide-react` for icons, `cn` for conditional `className`, and the Zodios client in `workers/web/src/app/utils/client/` for API calls from the app.
- The `@/` alias maps to `workers/web/src/app/*`; `@api/` maps to `workers/web/src/api/*`. UI/API contracts and pure domain logic live in `packages/shared` and use `@biccame/shared/...` imports. Neither UI nor backend imports the other layer.

## Secrets

- Never read or print `.env`, `.dev.vars`, or `.secrets`.
- Sync secrets only with `scripts/sync-cf-secrets.sh` (Worker secrets) and `scripts/sync-gh-secrets.sh` (`VITE_*` build values to GitHub Actions).
- `TWITTER_*` secrets live only in the bot Worker, never in the app Worker.

## Local-only tools and ports

- `bun run event-detect` writes only to the local D1 under `.wrangler/state`. Never point it at a remote database.
- e2e approved screenshots (`e2e/approved`) are committed only after a human reviews them. Never use `--update-snapshots`.
- The maintainer usually keeps `bun dev` running on port 15175 and `event-detect serve` on 15176. Do not start, stop, or restart them.
- Each e2e config starts its own Vite on a dedicated port, so e2e runs do not need those servers.

## PR review comments

Before starting work, check open PRs and their review feedback:

```sh
gh pr list
gh api repos/$(gh repo view --json nameWithOwner -q .nameWithOwner)/pulls/<number>/comments
gh api repos/$(gh repo view --json nameWithOwner -q .nameWithOwner)/pulls/<number>/reviews
gh api repos/$(gh repo view --json nameWithOwner -q .nameWithOwner)/issues/<number>/comments
```

If there are review comments (from Copilot or reviewers), show them to the user and ask whether to address them before changing anything.
